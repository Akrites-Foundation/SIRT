# Akrites SIRT & CVD Glossary

A shared vocabulary for the Akrites SIRT program and for Coordinated Vulnerability Disclosure (CVD) more broadly. Program-specific terms reflect current Akrites usage and may evolve as policies are ratified; for external standards, the linked source is authoritative.

Entries within each section are ordered alphabetically. Instructions for proposing changes or additions are included in the **[Contributing to the Glossary](#contributing-to-the-glossary)** section below.

---

## Program & governance

| Term | Definition |
|---|---|
| **Akrites** | The Akrites Foundation and its neutral Security Incident Response Team (the Akrites SIRT), coordinating vulnerability response across upstream open source projects. "OSS-SIRT" is an earlier synonym. |
| **Akrites staff** | Individuals employed by the Akrites Foundation, the Linux Foundation, or its fiscal sponsor to run the program, including SIRT staff. Staff are not members; they take part in cases under the same read-in rules. |
| **Case** | an Intake matter that the SIRT has classified for further processing and review. |
|**Case Material** | the materials generated by the WG in the process of analyzing, testing, and building patches or mitigations. |
| **Crit-Sit (Critical Situation)** | A case the SIRT Director declares serious enough to run as an incident — for example, confirmed active exploitation or a supply-chain compromise. See the [Critical Situation Playbook](./critical_situation_playbook.md). |
| **Front door** | The single Akrites intake path (private vulnerability reporting, SIRT@Akrites.dev, or the TAP intake API for members) that consolidates reports so upstream projects aren't approached through many uncoordinated channels. |
| **Governing Board (GB)** | The program's governing body; owns policy- and legal-level decisions. |
| **Incident Commander (IC)** | In a Crit-Sit, the SIRT case coordinator for the case, who runs the response and approves all read-ins. See the [Critical Situation Playbook](./critical_situation_playbook.md). |
| **Intake** | the SIRT's process for receiving reports, deduplicating, and processing certain reports as a Case. |
| **Member (member organization)** | An organization that has joined Akrites under its membership agreement. Used on its own, "member" always means the organization — refer to people as *member engineers*, *WG members*, or *staff*. Membership level carries no additional access to case information. |
| **Member engineer** | An individual employed by a member organization, or that member's authorized and approved delegate, who participates in Akrites work. Member engineers are read in to cases only through the [Read-In Policy](./Akrites-Read-In-Policy.md). |
| **PSIRT** | Product Security Incident Response Team — a vendor's or project's own product-security response function; Akrites coordinates with these. |
| **SIG** | Special Interest Group — a group formed around technology surrounding a WG's focus area. |
| **SIRT** | Security Incident Response Team — the Akrites staff and infrastructure that coordinate intake, disclosure, and upstream engagement. Major incidents are run under the [Critical Situation Playbook](./critical_situation_playbook.md). |
| **SIRT case coordinator** | The SIRT staff member accountable for a case: evaluates read-ins, assigns tiers, runs the timeline, and executes publication. |
| **SIRT Director** | Leads the Akrites SIRT; the escalation point after the case coordinator and an independent coordinator review, before the Governing Board (CVD Policy §15). |
| **Upstream** | the original open source project for the software being worked on. |
| **WG member** | An individual on a Working Group's membership register, read in under the [Read-In Policy](./Akrites-Read-In-Policy.md) §7. Only member engineers and approved delegates are eligible. WG membership does not by itself grant access to any case. |
| **Working Group (WG)** | A small, private, self-organizing team of read-in members that analyzes, tests, and patches vulnerabilities in a specific domain. |

## Disclosure process & concepts

| Term | Definition |
|---|---|
| **AI class (A / B / C)** | The oversight level for an AI-assisted task: **A** triage (sampling audit), **B** analysis (human review before sharing), **C** generation (full verification and named human sign-off). See the [AI Operations Guidelines](./ai_operations_guidelines.md). |
| **AI-assisted (discovery / analysis / patching)** | A capability-level label stating that AI/LLM tooling materially helped with a phase of the work. Published for both the finder and the SIRT; see [Attribution and AI-Use Disclosure Policy](./ai-use-disclosure.md). |
| **AI-use disclosure** | The requirement that every case records, and every advisory states, whether and how AI/LLM tooling was used — for both the finder and the Akrites SIRT (Coordinator), including an explicit "no AI tooling was used" where that applies. |
| **Alpha patch** | An early candidate fix shared with the WG and finder for review and testing before broader coordination. |
| **Blameless postmortem** | A no-fault review focused on systems rather than individuals. Required after an embargo break, an AI or automation failure, a missed CVD Policy commitment, or a Crit-Sit — see [Communications Playbook](./sirt-communications-playbook.md) Play 18. |
| **CVD** | Coordinated Vulnerability Disclosure — the practice of privately reporting a flaw, coordinating a fix under embargo, and disclosing publicly in a synchronized way. |
| **Deviation notice** | A short note published with the advisory when the SIRT's severity assessment differs materially from another party's published score, stating which metrics and assumptions differ — sharing the evidence rather than disputing the other party. See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). |
| **Embargo** | The agreed period of confidentiality before public disclosure, during which only read-in parties know of the issue. Akrites' proposed upstream embargo is 15 business days (leading to a total target time to PD of ≤ 17 bd Low/Med, ≤ 21 bd High, ≤ 24 bd Critical), deferring to the upstream project's own policy. |
| **Exploit state** | A separate, changing record of real-world exploitation evidence: **Active**, **Demonstrated**, **PoC**, **Theoretical**, or **Unknown** ("Unknown" never means safe). See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). |
| **Finder / Co-finder** | The party (or parties) who discovered and reported the vulnerability; co-finder rules govern shared attribution — see the [Attribution and AI-Use Disclosure Policy](./ai-use-disclosure.md). |
| **Hand-off (upstream)** | The point at which the SIRT formally engages the affected project with the validated finding. It starts the 15-business-day upstream disclosure period; the Finder is told the date in writing (CVD Policy §7). |
| **IR** | Incident Response. |
| **Least privilege** | The principle that access is scoped to only what a role needs; members see only the WGs they belong to, and only SIRT staff have cross-cutting visibility. |
| **Mitigation / workaround** | A non-patch means of reducing risk (e.g., a configuration change or firewall rule) when no fix is yet available. |
| **MoLR (Maintainer of Last Resort)** | A governed, per-CVE exception in which Akrites ships a security fix for an abandoned project under an Akrites-controlled namespace. It does not adopt or maintain the project. Requires Governing Board approval. See the [MoLR Policy](./Maintainer_of_Last_Resort_Policy.md). |
| **PD (Public Disclosure)** | The point at which meaningful information about a vulnerability becomes available to the general public without restriction — intentionally (the coordinated release on the PD date) or unintentionally (a leak or embargo break). See [What Counts as Public Disclosure](./what-counts-as-public-disclosure.md). |
| **PD date (Coordinated Release Date, CRD)** | The pre-agreed date and time for intentional public disclosure, set once a fix is available and an identifier assigned. |
| **POC** | Proof of Concept - a controlled demonstration or set of instructions that proves a reported software flaw is real and exploitable, typically used by security teams to validate risks, reproduce issues, and test patches. [TechTarget](https://www.techtarget.com/searchsecurity/definition/proof-of-concept-PoC-exploit) |
| **POV** | Proof of Vulnerability - Proof of Vulnerability (PoV) is an executable test case, input, or script that definitively confirms a theoretical security flaw is real, reproducible, and exploitable in a specific environment. In the context of vulnerability response and management, it serves as concrete, hands-on evidence that an identified software weakness can be triggered to compromise a system's confidentiality, integrity, or availability. [arXiv](https://arxiv.org/html/2607.12316v1) |
| **Read-in** | Granting a named individual access to a specific case or WG after they clear the Three-Gate Test (need-to-know, capacity to contribute, vetted identity) and the prerequisites. See the [Read-In Policy](./Akrites-Read-In-Policy.md). |
| **Read-out notice** | The message sent at PD to everyone on a case's read-in list confirming the embargo has ended and their access has closed. See the [Critical Situation Playbook](./critical_situation_playbook.md). |
| **Severity label** | The plain-language severity of a vulnerability — **Critical**, **High**, **Medium**, or **Low** — informed by its CVSS v4.0 score; it sets the case's PD target (CVD Policy §8). See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). |
| **SIREN** | The OpenSSF's public threat-intelligence mailing list ([announced May 2024](https://openssf.org/blog/2024/05/20/enhancing-open-source-security-introducing-siren-by-openssf/); modeled on oss-security), staffed and funded by the OpenSSF: a post-disclosure channel for sharing active threat activity affecting open source at large — exploitation campaigns, TTPs, and indicators of compromise (for example, spearphishing campaigns using fake GitHub token-renewal notices). The SIRT fires a SIREN post alongside the member notice at PD. |
| **SSVC (Stakeholder-Specific Vulnerability Categorization)** | CISA's decision tree (outcomes Track, Track\*, Attend, Act) that the SIRT uses internally to set response priority. Never published. See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). |
| **Steward / LTS** | A party that takes on long-term support or maintenance of a project; the preferred alternative to Akrites acting as MoLR. |
| **Synchronized disclosure** | Coordinating parties so the fix, advisory, and disclosure land together rather than piecemeal. |
| **Technical contribution ("price of admission")** | The expectation (CVD Policy §12) that members, reporters, and read-in members, contribute meaningfully — analysis, a patch, tests, or staging — rather than only reporting or observing. |
| **Tier 0 / 1 / 1.5 / 2 / 3 / 3.5** | The read-in tiers: **0** Finder & SIRT; **1** SME analysts/patch authors; **1.5** upstream maintainer/security team of the affected project (member or not); **2** patch testers, distribution partners / pre-disclosure rings; **3** second-order distributors (CDNs, registries); **3.5** international coordinators (≤ 24 h before PD). |
| **Tiered disclosure** | Reading parties in across staged tiers (0–3.5), each later tier seeing less and being read in later. |
| **VDR (Vulnerability Disclosure Report)** | The package the SIRT prepares to drive maintainer engagement and disclosure. |

## Roles & parties

| Term | Definition |
|---|---|
| **Clearinghouse** | A trusted external coordinator (e.g., a national CERT) or vendor program that reports to or through the SIRT on behalf of others. Also a reporter class in CVD Policy §12, and a credit option in which the organization is named as finder without its individual analysts. |
| **CNA (CVE Numbering Authority)** | An organization authorized to assign CVE IDs within its scope. |
| **Consumer / end user** | The party who must act on a disclosure once public; served at public disclosure, not before. |
| **Coordinator** | The neutral party facilitating a CVD case — for Akrites cases, the Akrites SIRT (individually, the SIRT case coordinator). Appears as "Coordinator (Akrites SIRT)" in advisory AI-use lines. |
| **Distribution / staging party** | A downstream distributor (e.g., package registry, CDN) read in late to pre-stage a fix for rapid propagation (Tier 2/3). |
| **Maintainer** | The upstream owner of the affected project; retains final say on the fix and disclosure timing, except where active exploitation or a public embargo break requires acceleration (CVD Policy §9). |
| **Owner** | The maintainer, security team, or organization responsible for a project's code and its security posture. The Akrites SIRT is usually the coordinator, not the Owner. See CVD Policy §3. |
| **SME** | Subject-Matter Expert — a member with domain expertise who analyzes or produces fixes (Tier 1) or tests them (Tier 2). |

## Data handling & classification

| Term | Definition | Reference |
|---|---|---|
| **Assume-exposed** | Handling posture for material that may already have left a trusted boundary (e.g., pasted into a public AI service). Such a report is treated as having **no embargo available** and is coordinated on an accelerated basis. | — |
| **Confidential AI tooling** | AI/LLM tooling that preserves confidentiality — self-hosted or enterprise models with contractual no-training and confidentiality terms, or the SIRT's own hardened analysis environment. Using it keeps the embargo option open. | — |
| **Need-to-know** | The requirement that a person genuinely requires the information to perform a role in the case. | — |
| **Public LLM tooling** | Public, hosted large-language-model services. Prompts and pasted material may be retained, logged, or used for training, so they are **not** confidential; a report developed with them is treated as assume-exposed. | — |
| **PVR (Private Vulnerability Reporting)** | A project's supported private channel for receiving vulnerability reports (e.g., GitHub's PVR feature). Akrites encourages projects to enable it. | — |
| **SBOM (Software Bill of Materials)** | A formal inventory of the components in a piece of software. | [cisa.gov/sbom](https://www.cisa.gov/sbom) |
| **TLP (Traffic Light Protocol)** | A standard set of labels governing how far information may be shared. | [first.org/tlp](https://www.first.org/tlp/) |
| **TLP:AMBER** | Need-to-know sharing within the recipient's organization **and its clients**. Akrites uses it for downstream staging (Tiers 3, 3.5). | [first.org/tlp](https://www.first.org/tlp/) |
| **TLP:AMBER+STRICT** | Need-to-know sharing within the recipient's **organization only**. Akrites' default for verification and remediation material. | [first.org/tlp](https://www.first.org/tlp/) |
| **TLP:GREEN** | Sharing within a community, but not public. Akrites uses it only for non-case material (e.g., sanitized postmortem summaries, trend reports) — never for case material before PD. | [first.org/tlp](https://www.first.org/tlp/) |
| **TLP:RED** | For named recipients only — no onward sharing, including within one's own organization. | [first.org/tlp](https://www.first.org/tlp/) |

## Standards, identifiers, scores & formats

| Term | Definition | Reference |
|---|---|---|
| **CSAF (Common Security Advisory Framework)** | An OASIS standard for machine-readable security advisories (and VEX). | [OASIS](https://www.oasis-open.org/) |
| **CVE (Common Vulnerabilities and Exposures)** | The global catalog of unique identifiers for publicly known vulnerabilities; operated by MITRE, sponsored by CISA. | [cve.org](https://www.cve.org/) |
| **CVSS (Common Vulnerability Scoring System)** | An open framework for scoring vulnerability severity (0–10). Akrites publishes CVSS v4.0 (current since Nov 2023) and does not produce v3.1 scores. See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). | [first.org/cvss](https://www.first.org/cvss/) |
| **CWE (Common Weakness Enumeration)** | A community catalog of software and hardware weakness *types* (the class of flaw), distinct from a specific CVE instance. | [cwe.mitre.org](https://cwe.mitre.org/) |
| **EPSS (Exploit Prediction Scoring System)** | A model estimating the probability that a published CVE will be exploited in the wild. Akrites does not use it for embargoed cases (there is no EPSS value before a CVE exists); it may inform priority once a CVE is public. See the [Severity Scoring Guidelines](./severity_scoring_guidelines.md). | [first.org/epss](https://www.first.org/epss/) |
| **KEV (Known Exploited Vulnerabilities)** | CISA's catalog of vulnerabilities with confirmed active exploitation. | [cisa.gov/kev](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) |
| **OSV** | An open, distributed database and schema for vulnerabilities in open source. | [osv.dev](https://osv.dev/) |
| **VEX (Vulnerability Exploitability eXchange)** | A machine-readable statement of whether a product is actually affected by a given vulnerability; commonly expressed via CSAF. | [OASIS](https://www.oasis-open.org/) |

# Contributing to the Glossary

Thanks for helping keep the **Akrites SIRT & CVD Glossary** accurate and useful. This is a lightweight process — most changes are a one-line edit and a pull request.

## What belongs here

- Terms and acronyms used routinely in the Akrites SIRT program or in Coordinated Vulnerability Disclosure.
- Program-specific vocabulary (e.g., read-in tiers, tooling names) and external standards (e.g., CVE, CVSS, TLP).

Leave out one-off jargon, project code names that aren't in general use, and anything already covered by an existing entry.

## Entry format

Each entry is a single table row in the appropriate section:

```markdown
| **Term (Expansion if it's an acronym)** | One or two sentences, plain language. | [label](https://link) |
```

## Style rules

- **Alphabetical order within each section** — place your entry in the correct spot; don't append to the end.
- Sort by the visible term, case-insensitively (e.g., `akrites.dev` before `AVID`).
- Bold the term with `**…**`. Put an acronym's expansion in parentheses.
- Match the existing sections; if a term doesn't fit any, propose a new section in your PR description rather than inventing one silently.
- Use en dashes/em dashes consistently with the rest of the file and keep links as `[short-label](url)`.

## How to propose a change

1. **Small change (add/edit one term):** open a pull request that edits `Akrites_SIRT_CVD_Glossary.md` directly.
2. **Not sure about wording, scope, or where it belongs:** open a **Discussion** (or an issue) first and tag the Policy/Process work stream.
3. In the PR description, note: the term, why it's needed, and — for external standards — the source you used.

## Review

The **Policy/Process work stream** reviews glossary PRs. Reviewers check that the entry is accurate, concise, correctly placed alphabetically, sourced (for external terms), and consistent with ratified policy. Program-specific definitions may be adjusted to stay aligned with current policy as it evolves.

## Copy-paste templates

Two-column section (no reference):

```markdown
| **Your Term** | Concise definition. |
```

Three-column section (with reference):

```markdown
| **Your Term** | Concise definition. | [source](https://example.org) |
```
